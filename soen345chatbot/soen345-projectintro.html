🧭 Different questions require different models

There is no single “best” way to test a program. Criteria give you systematic ways to decide what should be exercised.

CRITERIA MAP
🧩

Input Space Partitioning

Model the possible inputs as characteristics and blocks. Choose representative values instead of trying every possible input.

Tester question: “What different kinds of input behavior exist?”
🗺️

Graph Coverage

Model software as nodes, edges, and paths. Tests are selected to exercise required elements or paths in the model.

Tester question: “What behaviors or transitions must the system traverse?”
🧠

Logic Coverage

Test logic clauses as predicates and clauses. Investigate how individual conditions influence the overall decision.

Tester question: “Which conditions can actually change the decision?”
🔍

Data Flow Coverage

Model where values are defined and where they are subsequently used. Tests target important definition-use relationships.

Tester question: “Where does this value come from, and where does it go?”
🧬

Syntax-Based / Mutation Testing

Model likely faults through systematic program changes, then ask whether the test suite can distinguish the original from the mutant.

Tester question: “Could my tests detect a plausible change in the program?”
🐞

Fault-Oriented Thinking

Start from ways the software might be wrong and design tests capable of exposing those failures.

Tester question: “What mistake could a developer realistically have made?”
💡 The big idea

A testing criterion is a way of modeling the problem. The model determines what counts as a testing requirement, and those requirements guide the tests you construct.

SOEN PROJECT SETUP

👥 Learn together, test independently

You work in a group, but each student selects a different app. Everyone practices the same testing techniques while seeing how they apply to different apps.

INDIVIDUAL CONTRIBUTION

🧑‍💻 Your work can stand on its own

Each student can complete their testing activities independently. Group discussion is for sharing insights and comparing approaches, so one student's progress does not depend on another student's contribution.

Why this structure? If a group member contributes little or not at all, another student's progress is not blocked. Students who actively collaborate can still learn from how their peers test different apps.
